---
title: Migrating from mkdocstrings
description: Map an mkdocstrings-python configuration onto starlight-pydocs, and what differs.
---

Both plugins render the same model. [Griffe](https://mkdocstrings.github.io/griffe/), the static
analyser mkdocstrings-python already runs, produces it, and starlight-pydocs runs Griffe the same
way. Your docstrings, your anchors and your published `objects.inv` come across unchanged, so deep
links into your documentation and the projects that link into it keep working.

## Configuration

This handler configuration:

```yaml title="mkdocs.yml" {5-6,8-9,10-11,13-15}
plugins:
  - mkdocstrings:
      handlers:
        python:
          # 1. paths -> search
          paths: [src]
          options:
            # 2. docstring_style -> docstringStyle
            docstring_style: google
            # 3. show_source -> sourceLink
            show_source: true
            filters: ["!^_"]
          # 4. inventories -> inventories
          inventories:
            - url: https://docs.python.org/3/objects.inv
```

becomes this, with the same four options at the matching numbers:

```js title="astro.config.mjs" {14-15,16-17,18-19,22-23}
import starlight from '@astrojs/starlight';
import { defineConfig } from 'astro/config';
import starlightPydocs, { pydocsSidebarGroup } from 'starlight-pydocs';

export default defineConfig({
  integrations: [
    starlight({
      title: 'mypkg',
      plugins: [
        starlightPydocs({
          packages: [
            {
              name: 'mypkg',
              // 1. paths -> search
              search: ['../src'],
              // 2. docstring_style -> docstringStyle
              docstringStyle: 'google',
              // 3. show_source -> sourceLink
              sourceLink: { host: 'github', repo: 'you/mypkg', ref: 'main', root: '..' },
            },
          ],
          // 4. inventories -> inventories
          inventories: ['python'],
        }),
      ],
      sidebar: [{ label: 'API reference', items: [pydocsSidebarGroup] }],
    }),
  ],
});
```

`search` is resolved against the Astro project root, so a docs site living in `docs/` reaches its
Python sources with `../src`.

Underscore-prefixed members are hidden by default, so `filters: ["!^_"]` needs no counterpart.
`filters: { private: true }` asks for the opposite.

Each remaining handler option and its equivalent here:

| `mkdocs.yml` (`plugins.mkdocstrings.handlers.python`) | starlight-pydocs                                                |
| ----------------------------------------------------- | --------------------------------------------------------------- |
| `paths: [src]`                                        | `packages[].search: ['../src']` (relative to the Astro project) |
| `docstring_style: numpy`                              | `packages[].docstringStyle: 'numpy'`                            |
| `docstring_options: {…}`                              | `packages[].docstringOptions: {…}`                              |
| `members: [A, B]` / `members: false`                  | `packages[].members.include` (globs on dotted paths)            |
| `filters: ["!^_"]`                                    | `packages[].filters` plus `packages[].members.exclude`          |
| `inherited_members: true`                             | `packages[].filters.inherited` (already `true`)                 |
| `show_source: true`                                   | `packages[].sourceLink` (a forge preset or a template)          |
| `inventories: [{url: …}]`                             | top-level `inventories: [{ url, base? }]` or `'python'`         |
| `extensions: [griffe_pydantic]`                       | `packages[].extensions`, plus `extraRequirements`               |
| `::: mypkg.Report` in a page                          | `<Autodoc name="mypkg.Report" />` in an `.mdx` page             |
| `heading_level: 3`                                    | `<Autodoc … headingLevel={3} />`                                |
| `paths` + several handlers                            | several entries in `packages`                                   |
| `mkdocstrings` installed in the docs environment      | nothing: `uv` or a pre-generated dump                           |

## Shared features

- Docstrings: google, numpy and sphinx, parsed by the same Griffe parsers with the same options.
- Anchors: `#mypkg.report.Report.generate`, the dotted object path, as mkdocstrings emits it.
- `__all__`: a module that declares it publishes that list, otherwise visibility heuristics apply.
  Filters and glob selection then refine the result. An object missing after the move is almost
  always `__all__` or a filter, not extraction.
- `objects.inv`, in both directions: same names, roles and anchors, so other projects'
  `intersphinx_mapping` entries keep resolving, and you can consume any inventory you consume today.
- Cross-references in prose: `[title][mypkg.thing]` and `[mypkg.thing][]`, resolved against your own
  package first, then the inventories.
- `__init__` merged into the class, inherited members with provenance, positional-only and
  keyword-only markers, property and classmethod badges.

## Differences

### Page layout

Pages are generated rather than placed by hand. `mypkg` is documented at `/api/mypkg/`, each
submodule at `/api/mypkg/<module>/`, nested to mirror the package; `base` moves the whole tree.

They are injected routes rather than `.md` files written into `src/content/docs`, because Markdown
is a lossy intermediate for an API reference: `dict[str, float] | None` needs escaping everywhere
before its parts can be linked, heading IDs go through a slugger instead of being the dotted object
path, and there is nowhere to hang symbol-level search metadata. Nothing is written into your
content directory, and `astro dev` reflects a source change without rewriting files.

Members are documented on their module's page, so `mypkg.report.Report.generate` is a heading on
`/api/mypkg/report/`. That matches an mkdocstrings site with one `:::` per module, the common
layout.

There is no page-per-symbol mode. If your mkdocstrings site has one page per class, those URLs
change; the anchors within the module page do not.

A package entry is identified by its URL base, and mkdocstrings has no such notion. The same import
name may be documented at several bases, one per release, which is how
[versioned docs](/starlight-pydocs/guides/versioned-docs/) work.

### The `:::` directive becomes `<Autodoc>`

Generated pages cover whole modules, so `:::` is only needed where you want one object in the middle
of your own prose. `<Autodoc>` does that, rendering the object exactly as the generated pages do at
whatever heading level you ask for:

```mdx title="src/content/docs/reference.mdx"
import { Autodoc } from 'starlight-pydocs/components';

<Autodoc name="mypkg.Report" headingLevel={3} />
```

When the same import name is documented at more than one base, `<Autodoc package="…">` takes the
base. See [Autodoc](/starlight-pydocs/guides/autodoc/).

### Extraction runs as a subprocess

Griffe runs as `griffe dump`, found through `uv` or through an interpreter that already has it, so
nothing needs installing into a docs environment the way `mkdocstrings` does. It is static analysis,
so your package is never imported. You can also skip the subprocess entirely and commit a
[pre-generated dump](/starlight-pydocs/guides/pregenerated-dumps/), which is the route for CI
without Python.

### Extension points

There are no mkdocs hooks and no plugin ecosystem: nothing maps to `hooks.py`,
`mkdocs-gen-files` or `mkdocs-literate-nav`. Templates are Astro components rather than Jinja —
nine of them, with typed props.

What replaces them:

- [Component overrides](/starlight-pydocs/guides/component-overrides/) swap any of those nine for
  your own, everywhere they render.
- [Theme tokens](/starlight-pydocs/guides/theming/) restyle the output without replacing anything.
- The [Content Layer loader](/starlight-pydocs/guides/vanilla-astro/#the-content-layer-loader) is a
  typed way of building custom pages from the same model.

### Not supported

Most `show_*` options do not exist. Signatures, source links, badges, member summaries and
inherited members always render; CSS and component overrides are how you change them.

`@typing.overload` signatures are not shown yet. Griffe's `Function.as_dict` does not serialise
overloads, so the dump only contains the implementation. The renderer stacks overload signatures
when a dump carries them, so a future Griffe release fixes this.
