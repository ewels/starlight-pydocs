---
title: Migrating from mkdocstrings
description: Map an mkdocstrings-python configuration onto starlight-pydocs, and what differs.
---

Both plugins render the same model: Griffe's. Your docstrings, your anchors and your published
`objects.inv` come across unchanged, so deep links and the projects that link into your
documentation keep working.

## Configuration

Each handler option and its equivalent here:

| `mkdocs.yml` (`plugins.mkdocstrings.handlers.python`) | starlight-pydocs                                                |
| ----------------------------------------------------- | --------------------------------------------------------------- |
| `paths: [src]`                                        | `packages[].search: ['../src']` (relative to the Astro project) |
| `docstring_style: numpy`                              | `packages[].docstringStyle: 'numpy'`                            |
| `docstring_options: {…}`                              | `packages[].docstringOptions: {…}`                              |
| `members: [A, B]` / `members: false`                  | `packages[].members.include` (globs on dotted paths)            |
| `filters: ["!^_"]`                                    | `packages[].filters` plus `packages[].members.exclude`          |
| `inherited_members: true`                             | `packages[].filters.inherited` (already `true`)                 |
| `show_source: true`                                   | `packages[].sourceLink` (a forge preset or a template)          |
| `inventories: [{url: …}]`                             | top-level `inventories: [{ url, base? }]` or `'python'`         |
| `extensions: [griffe_pydantic]`                       | `packages[].extensions`, plus `extraRequirements`               |
| `::: mypkg.Report` in a page                          | `<Autodoc name="mypkg.Report" />` in an `.mdx` page             |
| `heading_level: 3`                                    | `<Autodoc … headingLevel={3} />`                                |
| `paths` + several handlers                            | several entries in `packages`                                   |
| `mkdocstrings` installed in the docs environment      | nothing: `uv` or a pre-generated dump                           |

For example, this `mkdocs.yml`:

```yaml
# mkdocs.yml
plugins:
  - mkdocstrings:
      handlers:
        python:
          paths: [src]
          options:
            docstring_style: google
            show_source: true
            filters: ["!^_"]
          inventories:
            - url: https://docs.python.org/3/objects.inv
```

becomes:

```js
// astro.config.mjs
import starlight from '@astrojs/starlight';
import { defineConfig } from 'astro/config';
import starlightPydocs, { pydocsSidebarGroup } from 'starlight-pydocs';

export default defineConfig({
  integrations: [
    starlight({
      title: 'mypkg',
      plugins: [
        starlightPydocs({
          packages: [
            {
              name: 'mypkg',
              search: ['../src'],
              docstringStyle: 'google',
              sourceLink: { host: 'github', repo: 'you/mypkg', ref: 'main', root: '..' },
            },
          ],
          inventories: ['python'],
        }),
      ],
      sidebar: [{ label: 'API reference', items: [pydocsSidebarGroup] }],
    }),
  ],
});
```

Underscore-prefixed members are hidden by default, so `filters: ["!^_"]` needs no counterpart.
`filters: { private: true }` asks for the opposite.

## Shared features

- Docstrings: google, numpy and sphinx, parsed by the same Griffe parsers with the same options.
- Anchors: `#mypkg.report.Report.generate`, the dotted object path, as mkdocstrings emits it.
- `__all__`: a module that declares it publishes that list, otherwise visibility heuristics apply.
  Filters and glob selection then refine the result. An object missing after the move is almost
  always `__all__` or a filter, not extraction.
- `objects.inv`, in both directions: same names, roles and anchors, so other projects'
  `intersphinx_mapping` entries keep resolving, and you can consume any inventory you consume today.
- Cross-references in prose: `[title][mypkg.thing]` and `[mypkg.thing][]`, resolved against your own
  package first, then the inventories.
- `__init__` merged into the class, inherited members with provenance, positional-only and
  keyword-only markers, property and classmethod badges.

## Differences

- Pages are generated rather than placed by hand. `mypkg` is documented at `/api/mypkg/`, each
  submodule at `/api/mypkg/<module>/`, nested to mirror the package; `base` moves the whole tree.
- Members are documented on their module's page, so `mypkg.report.Report.generate` is a heading on
  `/api/mypkg/report/`. That matches an mkdocstrings site with one `:::` per module, the common
  layout.
- There is no page-per-symbol mode. If your mkdocstrings site has one page per class, those URLs
  change; the anchors within the module page do not.
- `<Autodoc>` replaces the `:::` directive for the exceptions: it renders one object exactly as the
  generated pages do, at whatever heading level you choose.
- No mkdocs hooks or plugin ecosystem: nothing maps to `hooks.py`, `mkdocs-gen-files` or
  `mkdocs-literate-nav`. The extension points are
  [component overrides](/starlight-pydocs/guides/component-overrides/),
  [theme tokens](/starlight-pydocs/guides/theming/) and the
  [Content Layer loader](/starlight-pydocs/guides/vanilla-astro/#the-content-layer-loader), a typed
  way of building the same custom pages.
- Templates are Astro components, not Jinja: nine of them, with typed props.
- Most `show_*` options do not exist. Signatures, source links, badges, member summaries and
  inherited members always render; CSS and component overrides are how you change them.
- `@typing.overload` signatures are not shown yet. Griffe's `Function.as_dict` does not serialise
  overloads, so the dump only contains the implementation. The renderer stacks overload signatures
  when a dump carries them, so a future Griffe release fixes this.
- A package is identified by its URL base. mkdocstrings has no such notion. The same import name may
  be documented at several bases, one per release, and `<Autodoc package>` takes the base when a
  name is documented more than once. See
  [Versioned docs](/starlight-pydocs/guides/versioned-docs/).
- Extraction is a subprocess. Griffe runs as `griffe dump`, found through `uv` or an interpreter
  that has it, or skipped entirely with a
  [pre-generated dump](/starlight-pydocs/guides/pregenerated-dumps/). It is static analysis, so your
  package is never imported.
