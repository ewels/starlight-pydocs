import { Steps } from '@astrojs/starlight/components';

Your docs site is a Node project and you would rather not add a Python toolchain to its build.
`griffe dump` writes the whole API surface of a package to a single JSON file, and the plugin reads
that file instead of running Griffe: no `uv`, no interpreter, no Python at all on the machine that
builds the site. The Python project produces the file; the docs site consumes it.

The same move covers a package whose environment is awkward to reproduce — compiled extensions,
private dependencies, a pinned Python version — and it is how
[versioned documentation](/starlight-pydocs/guides/versioned-docs/) freezes the API surface of a
release.

## What a dump costs you

A dump is a snapshot. Nothing in the docs build can refresh it, so the pages describe the API as it
was when the file was written, until something writes a new file: a release workflow, a scheduled
job, or you at the keyboard. For a pinned release that is exactly the point. For a dump meant to
track `main`, it is the thing that goes stale without telling anyone.

Three things change at build time:

- Griffe never runs, so the options that configure it — `docstringStyle`, `docstringOptions`,
  `extensions` and `forceInspection` — have no effect on a package with a `source`. They belong in
  the command that produces the dump. Member filters, source links, the sidebar and search still
  apply, because those are rendering concerns.
- There are no Python files to watch, so `astro dev` does not reload when you regenerate a dump.
  Restart the dev server.
- `versions: { refs }` ([version annotations](/starlight-pydocs/guides/version-annotations/)) has to
  extract each ref from a git checkout, so it cannot be combined with `source`. The config throws
  and tells you to document that release as its own `packages` entry.

## Generate, publish, point the config at it

<Steps>

1. Extract the API surface in the Python project, running from the repository root:

   ```sh /-f\b/ /-d\b/
   uvx --from griffe griffe dump -f -d google --search src mypkg -o api.json
   ```

   `-f` and `-d` are both load-bearing, and both are silent when omitted. See
   [the command in detail](#the-command-in-detail).

2. Publish the file where the docs build can read it. Dumps are read-only build inputs and compress
   well, so a release asset is enough:

   ```yaml title=".github/workflows/api-dump.yml" {21}
   name: Publish API dump

   on:
     release:
       types: [published]

   permissions:
     contents: write

   jobs:
     dump:
       runs-on: ubuntu-latest
       steps:
         - uses: actions/checkout@v7
         - uses: astral-sh/setup-uv@v7
         - name: Extract the API surface
           run: uvx --from griffe griffe dump -f -d google --search src mypkg -o api.json
         - name: Attach it to the release
           env:
             GH_TOKEN: ${{ github.token }}
           run: gh release upload "${{ github.event.release.tag_name }}" api.json
   ```

3. Point the package entry at the published URL:

   ```js title="astro.config.mjs" {5}
   starlightPydocs({
     packages: [
       {
         name: 'mypkg',
         source: { url: 'https://github.com/you/mypkg/releases/download/v2.1.0/api.json' },
       },
     ],
   });
   ```

</Steps>

Point at a tag for a pinned version, or upload to a stable location — an S3 bucket, a `latest`
release, a file on `gh-pages` — and let revalidation keep the site current.

## Downloads and the cache

`url` must be an `http(s)` URL. The download is cached under `cacheDir` (`node_modules/.astro` by
default) alongside the `ETag` and `Last-Modified` the server sent, and `cache` decides what the next
build does with it:

| `cache`        | Behaviour                                                                            |
| -------------- | ------------------------------------------------------------------------------------ |
| `'revalidate'` | Default. Sends `If-None-Match` / `If-Modified-Since`; a `304` reuses the cached copy. |
| `'force'`      | Never contacts the server when a cached copy exists. Fastest, and offline-safe.       |
| `'bypass'`     | Downloads on every build.                                                             |

If the host is unreachable or answers with an error and a cached copy exists, the build logs a
warning and uses the copy: a documentation build should not fail because a release asset was briefly
unavailable. With no cached copy it fails, and the message names the URL and the status.

:::caution[A dump is content for your site]
Everything in the dump ends up rendered on your pages, and markdown passes raw HTML through
unsanitised (the same trust model as mkdocstrings). Treat a dump like the rest of your docs: only
use dumps whose provenance you trust.
:::

## Committing the dump instead

Ship the dump inside the docs repository for a build that touches no network and a change you can
review in a pull request:

```js title="astro.config.mjs" {2}
starlightPydocs({
  packages: [{ name: 'mypkg', source: { file: './dumps/mypkg.json' } }],
});
```

`file` is resolved relative to the Astro project root, and a missing file fails the build naming the
path it looked for. A dump is a large JSON file, so expect noisy diffs; a repository that dislikes
that is better served by the URL form.

## Extraction order

The plugin picks how to get a dump in a fixed order: an explicit `runner.command`, then a `source`
dump, then `uvx --from griffe`, then `python -m griffe`. A `runner.command` therefore beats
`source` — set one globally and every package runs it, including the ones that carry a `source`.

## The command in detail

Without `uvx`, when `griffe` is already installed:

```sh /-f\b/ /-d\b/
griffe dump -f -d google --search src mypkg -o api.json
```

This is exactly what the plugin runs for itself. The flags:

- `-f` (`--full`) adds the file paths, line numbers and visibility flags that source links, member
  filtering and provenance are built from. Without it, every object arrives as a bare stub.
- `-d <style>` parses docstrings into structured sections — `google`, `numpy`, `sphinx` or `auto`.
  Without it, a docstring stays one raw string and no parameter table, returns block or admonition
  can be rendered.
- `--search` (`-s`) points at the directory containing the package, and can be repeated.
- `-o` writes the JSON; without it, griffe writes to standard output.

Add the flags your package needs, and keep them in step with what the docs site expects to render.
A pydantic model layer needs the Griffe extension installed alongside Griffe (`--with`) and enabled
(`-e`); `-D` takes parser options as JSON:

```sh /-D\b/ /-e\b/ "--with"
uvx --with griffe-pydantic --from griffe griffe dump -f -d google \
  -D '{"returns_named_value": false}' -e griffe_pydantic --search src mypkg -o api.json
```

## Source links with a dump from elsewhere

Source links are built from the paths griffe recorded, which were relative to the directory griffe
ran in. Run the dump command from the repository root and `{path}` is already repository-relative,
which is what a forge URL wants:

```js title="astro.config.mjs" {7-13}
starlightPydocs({
  packages: [
    {
      name: 'mypkg',
      source: { url: 'https://…/v2.1.0/api.json' },

      // No root: the paths in the dump are already
      // relative to the repository.
      sourceLink: {
        host: 'github',
        repo: 'you/mypkg',
        ref: 'v2.1.0',
      },
    },
  ],
});
```

Do not set `sourceLink.root` for a dump produced on another machine: `root` is applied to the
absolute path griffe recorded, which is a path on the CI runner and means nothing locally. `root` is
for the case where extraction runs on this machine and the sources sit outside the Astro project;
see [Source links](/starlight-pydocs/guides/source-links/).

Griffe's own `source_link` is another option: griffe 2 records a commit-pinned blob URL per object
when it runs inside a git checkout, so a dump made in CI often carries working links with no
`sourceLink` configuration at all.

## Checking a dump

A dump is an object keyed by package name, with the whole tree underneath:

```sh
jq 'keys' api.json                          # ["mypkg"]
jq '.mypkg.members | keys' api.json         # the top-level surface
jq '.mypkg.members.Report.docstring.parsed[0].kind' api.json   # "text" if -d ran
```

If `docstring.parsed` is missing, the dump was made without `-d` and the pages will carry signatures
with no parameter tables or admonitions. If objects have no `filepath`, it was made without `-f`,
and source links and the visibility-based member filters have nothing to work from. Neither is an
error the plugin can detect for you, because both produce thinner pages rather than a failed build.
Check a dump the first time a new pipeline produces one. A file that is not a griffe dump at all, or
does not contain the configured package, does fail, naming the file and listing what the dump does
contain.
