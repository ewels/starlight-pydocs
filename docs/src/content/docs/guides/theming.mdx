Every colour, corner radius and font on the generated pages goes through a `--pyd-*` custom
property, so retinting the pages is a handful of property declarations. Anything the tokens do not
cover is a normal CSS rule, and your rules win by default — see
[Overriding rules](#overriding-rules).

Swapping a whole renderer, so that signature blocks or member tables are built by an Astro
component of your own, is a different mechanism:
[Component overrides](/starlight-pydocs/guides/component-overrides/).

## Loading your stylesheet

The plugin's stylesheet is `starlight-pydocs/styles`. Under Starlight the plugin appends it to
Starlight's `customCss` for you; pass `injectStyles: false` if you would rather import it yourself.

Your own CSS goes in that same list, registered like any other Starlight custom stylesheet:

```js title="astro.config.mjs" {4}
starlight({
  title: 'My project',
  plugins: [starlightPydocs({ packages: [{ name: 'mypkg', search: ['../src'] }] })],
  customCss: ['./src/styles/custom.css'],
});
```

Both kinds of change live in that file. Retint by setting tokens; override by writing a rule:

```css title="src/styles/custom.css" {5-10}
:root {
  --pyd-accent: #b45309;
  --pyd-radius: 0;
}
/* Unlayered, so this rule beats the plugin
   stylesheet with no !important. */
.pyd-signature {
  background: transparent;
  border-inline-start: 3px solid var(--pyd-accent);
}
```

In a plain Astro project nothing is injected. The plugin's built-in page layout imports the
stylesheet itself, so the generated pages are styled either way. Import it yourself when you pass a
layout of your own as `layout`, or in a hand-written page that embeds API docs with
[`<Autodoc>`](/starlight-pydocs/guides/autodoc/):

```astro title="src/layouts/MyLayout.astro"
---
import 'starlight-pydocs/styles';
---
```

## Overriding rules

Every rule in the stylesheet is wrapped in `@layer starlight-pydocs`. Unlayered rules beat layered
ones whatever their specificity, so a plain selector in your own stylesheet wins with no specificity
fight and no `!important`. That is the whole trick, and it is worth knowing before you start
escalating selectors that were already going to work.

Keep your overrides unlayered and that holds however you load them. If you put your own rules in a
cascade layer, the comparison changes: the plugin appends its stylesheet after your `customCss`
entries, so its layer is declared last and later-declared layers win.

The one place it does not hold is inside Starlight's own `.sl-markdown-content`, where Starlight's
unlayered rules apply too. There, give your rule enough specificity to beat Starlight's, exactly as
the plugin's stylesheet does in the few places it must.

Class hooks are stable and prefixed `pyd-`. The ones worth knowing:

| Class                                 | What it wraps                                            |
| ------------------------------------- | -------------------------------------------------------- |
| `.pyd-module`                         | A whole module page's body                               |
| `.pyd-member`                         | One documented object, including its members             |
| `.pyd-heading`, `.pyd-anchor`         | An object's heading and its permalink                    |
| `.pyd-badges`, `.pyd-badge`           | Kind, label and deprecation badges                       |
| `.pyd-signature`                      | A signature block (`--overload`, `--attribute` variants) |
| `.pyd-type`                           | A name inside a signature or annotation (linked or not)  |
| `.pyd-provenance`, `.pyd-source-link` | The line under a heading                                 |
| `.pyd-section`, `.pyd-section-title`  | One docstring section and its heading                    |
| `.pyd-params`, `.pyd-summary-table`   | Parameter tables and member summaries                    |
| `.pyd-aside`                          | An admonition (`--tip`, `--caution`, `--danger`)         |
| `.pyd-inherited`                      | The `<details>` block of members from a base class       |
| `.pyd-search…`                        | The symbol search element and its results                |
| `.pyd-page`, `.pyd-toc`               | The built-in vanilla layout and its table of contents    |

For anything selective, reach for the data attributes instead: they carry the model's own
vocabulary, so `[data-pydocs-kind="class"]`, `[data-pydocs-path="mypkg.Report"]`,
`[data-pydocs-group="methods"]`, `[data-pydocs-section="parameters"]`,
`[data-pydocs-badge="deprecated"]` and `[data-pydocs-aside="note"]` all say what they mean.

## Tokens

Set any of these on `:root`, or on a narrower selector to retint one part of the site. The values
shown are the defaults: Starlight's token first, then a static fallback for sites without Starlight.

| Token               | Default                                   | Used for                                         |
| ------------------- | ----------------------------------------- | ------------------------------------------------ |
| `--pyd-text`        | `var(--sl-color-text, #24292f)`           | Body text in signatures and tables               |
| `--pyd-text-muted`  | `var(--sl-color-gray-3, #57606a)`         | Badges, provenance, section titles, source links |
| `--pyd-text-invert` | `var(--sl-color-black, #ffffff)`          | Text on an accent background (the kind badge)    |
| `--pyd-bg`          | `var(--sl-color-bg, #ffffff)`             | Page background in the built-in layout           |
| `--pyd-surface`     | `var(--sl-color-gray-6, #f6f8fa)`         | Signature blocks, badges, search results         |
| `--pyd-border`      | `var(--sl-color-hairline-light, #d8dee4)` | Member rules, table borders, input borders       |
| `--pyd-accent`      | `var(--sl-color-text-accent, #2563eb)`    | Linked types, anchors, the kind badge            |
| `--pyd-accent-low`  | `var(--sl-color-accent-low, #dbeafe)`     | Accent backgrounds                               |
| `--pyd-note`        | `var(--sl-color-blue, #3b82f6)`           | Note asides                                      |
| `--pyd-note-low`    | `var(--sl-color-blue-low, #dbeafe)`       | Note aside background                            |
| `--pyd-tip`         | `var(--sl-color-purple, #8b5cf6)`         | Tip asides                                       |
| `--pyd-tip-low`     | `var(--sl-color-purple-low, #ede9fe)`     | Tip aside background                             |
| `--pyd-caution`     | `var(--sl-color-orange, #ea580c)`         | Caution asides and deprecation badges            |
| `--pyd-caution-low` | `var(--sl-color-orange-low, #ffedd5)`     | Caution aside background                         |
| `--pyd-danger`      | `var(--sl-color-red, #dc2626)`            | Danger asides                                    |
| `--pyd-danger-low`  | `var(--sl-color-red-low, #fee2e2)`        | Danger aside background                          |
| `--pyd-radius`      | `0.375rem`                                | Corner radius on signatures and inputs           |
| `--pyd-mono`        | `var(--sl-font-mono, …)`                  | Every monospaced string                          |

Because the defaults reference Starlight's tokens, a Starlight site that changes its accent colour
changes the API pages with it. Retint one thing at a time when you do want to differ.

:::caution[Starlight's colour tokens are contrast tokens]
`--sl-color-white` is _dark_ in light mode: the names describe contrast, not literal colours. That
is why text on an accent background here is `--pyd-text-invert`, which defaults to Starlight's
`--sl-color-black`, following the same pattern as Starlight's own LinkButton. Substituting a literal
white breaks light mode.
:::

## Dark mode

Under Starlight there is nothing to do: the tokens follow `--sl-*`, which Starlight flips.

Without Starlight, the stylesheet defines a dark palette twice, so both ways of choosing a theme
work: under `@media (prefers-color-scheme: dark)` guarded by `:root:not([data-theme='light'])`, and
under `:root[data-theme='dark']`. Set `data-theme="dark"` or `data-theme="light"` on `<html>` from
your own theme toggle and the API pages follow; leave it unset and they follow the operating system.

## Code inside docstrings

Fenced blocks and doctest transcripts in a docstring are highlighted by the site's own pipeline,
because docstring prose renders through the Markdown processor your project configured. There is no
separate Shiki configuration here, and nothing to keep in sync.

Under Starlight that means Expressive Code, so a docstring's code block gets the same frame, copy
button and themes as a code block in a hand-written page. In a plain Astro project it is Shiki's
`.astro-code` output, configured by `markdown.shikiConfig`:

```js title="astro.config.mjs" {4-5}
export default defineConfig({
  markdown: {
    shikiConfig: {
      themes: { light: 'github-light', dark: 'github-dark' },
      defaultColor: false,
    },
  },
});
```

Two themes with `defaultColor: false` emit both palettes as custom properties, which is what makes a
single stylesheet work in light and dark. This site uses exactly that configuration.

Signatures are not Shiki output. They are built from the model so that every type can be a link, and
they are styled with `.pyd-signature` and `.pyd-type` rather than syntax-highlighted. The trade is
deliberate: a linked `dict[str, Report]` is worth more on an API page than token colours.
