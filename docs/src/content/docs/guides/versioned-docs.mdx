---
title: Versioned docs
description: Document several releases of one package in one build, with pinned dumps and one sidebar group per version.
---

Generated pages are injected routes, not files in `src/content/docs`, which is what makes their
anchors, linked types and search metadata possible
([why](/starlight-pydocs/guides/migration/#page-layout)). It also means
[starlight-versions](https://starlight-versions.vercel.app/) does not snapshot them: it copies the
content collection into a per-version directory, and there is no file to copy for a route.

Versioning the API reference is therefore the plugin's job, and one plugin instance does it: add one
`packages` entry per release you want to keep, each with its own `base` and its own pinned dump. A
dump is a complete, frozen description of one release's API, and reading one needs no Python and no
checkout of that release.

## One entry per version

```js
// astro.config.mjs
starlightPydocs({
  packages: [
    {
      // The current release, extracted from the working tree.
      name: 'mypkg',
      search: ['../src'],
      sourceLink: { host: 'github', repo: 'you/mypkg', ref: 'v2.1.0', root: '..' },
    },
    {
      // The same import name again, at its own base and its own dump.
      name: 'mypkg',
      base: '1x/api/mypkg',
      label: 'mypkg 1.x',
      source: { url: 'https://github.com/you/mypkg/releases/download/v1.4.3/api.json' },
      sourceLink: { host: 'github', repo: 'you/mypkg', ref: 'v1.4.3', root: '..' },
    },
  ],
});
```

`name` is the import name, which every version shares; `base` is the identity of an entry, and
bases must be distinct and non-overlapping. `label` names the entry for humans (the sidebar group,
the `llms.txt` heading, the published inventory) and defaults to `name`.

Each entry is self-contained. It gets its own pages under its own base, its own `symbols.json`,
`objects.inv` and `llms.txt`, its own docstring rendering and its own model. Links stay inside the
entry that produced them: a type annotation, a member link or a docstring cross-reference on a 1.x
page resolves against the 1.x model, so `/1x/api/mypkg/report/#mypkg.report.Report` never links out
to the 2.x page of the same class. Resolution across entries deliberately skips entries with the
same import name, which is what keeps two documented versions from bleeding into each other.

This documentation site is built that way: `demopkg` is documented at `/api/demopkg/` from the
fixture source, and again at `/1x/api/demopkg/` from the checked-in dump.

## Pin the dump

An entry documenting a release must not be extracted from the working tree, or it will describe
whatever `main` looked like at build time. Pin it:

- `source: { url }` for a dump the release workflow published as a release asset.
- `source: { file }` for a dump committed into the docs site.

`sourceLink.ref` matching that release keeps the source links honest, because line numbers move
between releases. See [Pre-generated dumps](/starlight-pydocs/guides/pregenerated-dumps/) for how to
produce and publish `api.json`.

## Sidebar placement

Give each version its own placeholder from `createPydocsSidebarGroup()` and put it where that
version belongs:

```js
import starlightPydocs, { createPydocsSidebarGroup, pydocsSidebarGroup } from 'starlight-pydocs';

const legacyApi = createPydocsSidebarGroup();

export default defineConfig({
  integrations: [
    starlight({
      title: 'mypkg',
      plugins: [
        starlightPydocs({
          packages: [
            { name: 'mypkg', search: ['../src'] },
            {
              name: 'mypkg',
              base: '1x/api/mypkg',
              label: 'mypkg 1.x',
              source: { file: './dumps/mypkg-1.4.3.json' },
              sidebar: { group: legacyApi },
            },
          ],
        }),
      ],
      sidebar: [
        { label: 'API reference', items: [pydocsSidebarGroup] },
        { label: 'v1.x', collapsed: true, items: [legacyApi] },
      ],
    }),
  ],
});
```

## Alongside starlight-versions

starlight-versions is still the right tool for the prose: let it version the guides, and put each
API entry's group inside the matching version's sidebar. The version sidebars are ordinary
Starlight sidebars, so a placeholder works there exactly as it does above:

```js
starlight({
  plugins: [
    starlightVersions({ versions: [{ slug: '1.x' }] }),
    starlightPydocs({
      packages: [
        { name: 'mypkg', search: ['../src'] },
        {
          name: 'mypkg',
          base: '1x/api/mypkg',
          label: 'mypkg 1.x',
          source: { file: './dumps/mypkg-1.4.3.json' },
          sidebar: { group: legacyApi },
        },
      ],
    }),
  ],
  sidebar: [
    { label: 'Guides', autogenerate: { directory: 'guides' } },
    { label: 'API reference', items: [pydocsSidebarGroup] },
    { label: 'v1.x API', items: [legacyApi] },
  ],
});
```

Naming the archived base after the version slug starlight-versions uses (`1.x/api/mypkg` for its
`1.x` prose) keeps the two halves of a version in one place as far as readers are concerned.

## `<Autodoc>` needs the base

An import name identifies nothing once it is documented twice, so an `<Autodoc>` block that would
otherwise resolve by name has to say which entry it means, by base:

```mdx
<Autodoc name="mypkg.Report" package="api/mypkg" />
<Autodoc name="mypkg.Report" package="1x/api/mypkg" />
```

Without it the build stops and lists the candidate bases. `<SymbolSearch package="…" />` takes the
same value. Both also accept a plain import name where only one entry documents that package.

## One build per version instead

Documenting versions in one build keeps every release at a stable URL and one deployment. The
alternative — one site build per version, each pinning its own dump and deployed under its own path
prefix — is still available, and is the better fit when the prose differs so much between versions
that you want whole separate sites:

```js
// astro.config.mjs
const version = process.env.DOCS_VERSION ?? 'v2.1.0';
const isLatest = process.env.DOCS_LATEST === 'true';

export default defineConfig({
  site: 'https://docs.example.com',
  base: isLatest ? '/' : `/${version}`,
  integrations: [
    starlight({
      title: `mypkg ${version}`,
      plugins: [
        starlightPydocs({
          packages: [
            {
              name: 'mypkg',
              source: { url: `https://github.com/you/mypkg/releases/download/${version}/api.json` },
              sourceLink: { host: 'github', repo: 'you/mypkg', ref: version },
            },
          ],
        }),
      ],
      sidebar: [{ label: 'API reference', items: [pydocsSidebarGroup] }],
    }),
  ],
});
```

```sh
DOCS_VERSION=v2.1.0 DOCS_LATEST=true pnpm build && mv dist public-site
DOCS_VERSION=v1.4.3 pnpm build && mv dist public-site/v1.4.3
```

Every href the plugin emits goes through Astro's `base`, so the archived pages work under their
prefix with no further configuration.

:::note[Registering the plugin twice does not work]
Two `starlightPydocs()` instances in one Starlight config would share one virtual context module and
inject the same catch-all route, so the second instance's pages do not exist. Everything on this
page is one instance with several `packages` entries, which is the supported shape.
:::
