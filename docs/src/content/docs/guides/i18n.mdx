Every label the pages render (section headings, badges, table columns, the search box, the
permalink hint) comes from a translation table. Thirteen languages ship with the package, and
nothing needs configuring to use them.

## Bundled locales

| Locale  | Language              | Locale  | Language            |
| ------- | --------------------- | ------- | ------------------- |
| `en`    | English (the source)  | `nl`    | Dutch               |
| `de`    | German                | `no`    | Norwegian (Bokmål)  |
| `es`    | Spanish               | `pt-BR` | Portuguese (Brazil) |
| `fr`    | French                | `ru`    | Russian             |
| `it`    | Italian               | `sv`    | Swedish             |
| `ja`    | Japanese              | `zh`    | Chinese (simplified) |
| `ko`    | Korean                |         |                     |

Each locale overlays only the keys it translates, and English fills any gap, so a string added in a
new release is readable everywhere from the day it lands.

Labels that name a Python or pydantic construct are deliberately left in English in every locale:
`classmethod`, `staticmethod`, `async`, `abstract`, `cached`, `pydantic model`, `pydantic field` and
`pydantic validator` are the identifiers a reader sees in the code, and translating them would name
something that does not exist.

## In a Starlight site

The plugin injects its tables through Starlight's `i18n:setup` hook, so labels follow Starlight's
own locale selection with no extra configuration. A site with `locales` configured serves each
locale's pages with that locale's labels; a monolingual site with `defaultLocale: 'fr'` gets French
labels throughout.

```js
// astro.config.mjs
starlight({
  title: 'Mon projet',
  defaultLocale: 'fr',
  locales: { fr: { label: 'Français' }, en: { label: 'English' } },
  plugins: [starlightPydocs({ packages: [{ name: 'mypkg', search: ['../src'] }] })],
});
```

Generated pages themselves are not translated: there is one set of API pages, built from one dump,
and they carry the labels of whichever locale the reader is browsing. The docstrings are your
package's, in whatever language you wrote them.

### Changing or adding a string

The keys share Starlight's global translation table, namespaced `starlightPydocs.`, so overriding
one is the same as overriding any Starlight string:

```js
// src/content/i18n/fr.json
{
  "starlightPydocs.parameters": "Arguments",
  "starlightPydocs.viewSource": "Voir le code"
}
```

The same file is how you add a locale the package does not ship yet. If you translate a full set,
a pull request adding it to `translations.ts` is welcome. See
[Contributing](/starlight-pydocs/guides/contributing/).

## Without Starlight

There is no translation table to inject into a plain Astro project, so every component takes a
`labels` prop instead. It wins over everything, which also makes it the way to override one string
in one place inside a Starlight site:

```astro
---
import { Autodoc, SymbolSearch } from 'starlight-pydocs/components';
---

<Autodoc name="mypkg.Report" labels={{ parameters: 'Arguments', returns: 'Retourne', viewSource: 'Voir le code' }} />
<SymbolSearch labels={{ searchLabel: 'Rechercher un symbole', searchPlaceholder: 'Classes, fonctions, attributs…' }} />
```

The generated pages of a vanilla site are rendered by the route rather than by you, so there is no
`labels` prop to pass them. They read a translation function off `Astro.locals` instead (the same
mechanism Starlight's `t()` arrives through), so one middleware translates every generated page:

```ts
// src/middleware.ts
import { defineMiddleware } from 'astro:middleware';

const fr: Record<string, string> = {
  'starlightPydocs.parameters': 'Arguments',
  'starlightPydocs.viewSource': 'Voir le code',
  'starlightPydocs.onPage': 'Sur cette page',
};

export const onRequest = defineMiddleware((context, next) => {
  context.locals.t = (key: string) => fr[key] ?? key;
  return next();
});
```

Keys are namespaced exactly as in a Starlight table, and returning the key unchanged means "no
translation", which falls back to English. Without such a middleware, a vanilla site's generated
pages use the English defaults.

`locals.t` is your own addition to `App.Locals`, so declare it once for the type-checker:

```ts
// src/env.d.ts
declare namespace App {
  interface Locals {
    t: (key: string) => string;
  }
}
```

## The keys

Resolution order for every label is: the `labels` prop, then the host's translation for
`starlightPydocs.<key>`, then the bundled English default. The keys are grouped by what they label:

- Member groups: `attributes`, `properties`, `classes`, `functions`, `methods`, `modules`.
- Docstring sections: `parameters`, `otherParameters`, `typeParameters`, `returns`, `yields`,
  `receives`, `raises`, `warns`, `examples`, `notes`, `references`.
- Signatures and metadata: `bases`, `default`, `required`, `overload`, `overloads`,
  `inheritedFrom`, `reexportedFrom`, `aliasOf`, `deprecated`, `deprecatedSince`, `addedIn`,
  `viewSource`, `sourceCode`.
- Table columns: `columnName`, `columnType`, `columnDescription`, `columnDefault`.
- Kinds and labels: `kindModule`, `kindClass`, `kindFunction`, `kindMethod`, `kindAttribute`,
  `kindProperty`, `kindAlias`, and the `label*` badges.
- Search: `searchLabel`, `searchPlaceholder`, `searchNoResults`, `searchResults`, `searchHint`.
- Page furniture: `permalink`, `apiReference`, `overview`, `onPage`, `noMembers`, `undocumented`.

`lib/strings.ts` in the package is the authoritative list, and the unit tests check that every
locale's keys exist in it.
