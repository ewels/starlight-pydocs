Griffe parses your docstrings before this plugin renders anything, so what you write has to
be one of the four conventions it knows: `google` (the default), `numpy`, `sphinx`, or
`auto`. The style is a per-package setting, so one site can document packages written
differently.

```js title="astro.config.mjs" "docstringStyle"
starlightPydocs({
  packages: [
    { name: 'mypkg', search: ['../src'], docstringStyle: 'numpy' },
    { name: 'legacy', search: ['../legacy'], docstringStyle: 'sphinx' },
    { name: 'newpkg', search: ['../new'] },
  ],
});
```

A package that sets no style gets `google`. `auto` is the fourth choice: Griffe picks a
parser per docstring, which is what a package whose docstrings are not consistent needs.

Name any of the other three and it is the only parser Griffe tries. Point the `numpy` parser
at a google docstring and `Args:` is read as ordinary prose: no parameter table, no `Returns`
block, and a build that succeeds. Griffe's own warnings reach your build log prefixed
`griffe:`, but not every mis-parse produces one.

:::caution[A wrong style degrades silently]
A `docstringStyle` that does not match your docstrings never fails the build. It produces thin
pages instead, so open a rendered page after you change it.
:::

## The same docstring, three ways

<Tabs syncKey="docstring">
  <TabItem label="Google">

    ```python "Args:" "Returns:" "Raises:"
    def resample(grid: Grid, factor: float = 2.0) -> Grid:
        """Scale a grid by a factor.

        Args:
            grid: The grid to scale.
            factor: Multiplier applied to both dimensions.

        Returns:
            A new, scaled grid.

        Raises:
            ValueError: If `factor` is not positive.
        """
    ```

    A recognised title, a colon, and an indented block. This is the default, and what the
    `demopkg` fixture behind this site's [example pages](/starlight-pydocs/api/demopkg/) is
    written in. A parameter needs no type in the docstring: `name: description` is enough,
    because the annotation supplies the type.

  </TabItem>
  <TabItem label="NumPy">

    ```python /-{3,}/
    def resample(grid: Grid, factor: float = 2.0) -> Grid:
        """Scale a grid by a factor.

        Parameters
        ----------
        grid : Grid
            The grid to scale.
        factor : float, optional
            Multiplier applied to both dimensions.

        Returns
        -------
        Grid
            A new, scaled grid.

        Raises
        ------
        ValueError
            If `factor` is not positive.
        """
    ```

    The underline is what makes a section: leave one out and the title above it is read as
    prose. Types go on the parameter line itself, after a space-padded colon (`name : type`).
    Rendered: [`numpkg`](/starlight-pydocs/api/numpkg/).

  </TabItem>
  <TabItem label="Sphinx">

    ```python ":param" ":type" ":returns:" ":raises"
    def resample(grid: Grid, factor: float = 2.0) -> Grid:
        """Scale a grid by a factor.

        :param grid: The grid to scale.
        :param factor: Multiplier applied to both dimensions.
        :type factor: float
        :returns: A new, scaled grid.
        :raises ValueError: If `factor` is not positive.
        """
    ```

    reStructuredText field lists. Types come from a `:type name:` field, or from the
    annotation when there is none. The prose inside a field is rendered by your site's
    Markdown processor, and nothing this package adds understands reStructuredText, so write
    cross-references with the
    [mkdocstrings reference syntax](/starlight-pydocs/guides/cross-references/) rather than an
    rST role such as `:func:`. Rendered: [`sphpkg`](/starlight-pydocs/api/sphpkg/).

  </TabItem>
</Tabs>

All three arrive as the same structured sections, so all three render the same way: the
summary as prose, then a parameter table, then typed `Returns` and `Raises` blocks with the
exception type linked.

## Parser options

Griffe's parsers take options of their own, and `docstringOptions` passes them through as
griffe's `-D` flag:

```js title="astro.config.mjs" collapse={1-6, 20-27} {16-19}
import starlight from '@astrojs/starlight';
import { defineConfig } from 'astro/config';
import starlightPydocs, { pydocsSidebarGroup } from 'starlight-pydocs';

export default defineConfig({
  integrations: [
    starlight({
      title: 'My project',
      plugins: [
        starlightPydocs({
          packages: [
            {
              name: 'mypkg',
              search: ['../src'],
              docstringStyle: 'google',
              docstringOptions: {
                warn_unknown_params: false,
                returns_named_value: false,
              },
            },
          ],
        }),
      ],
      sidebar: [{ label: 'API reference', items: [pydocsSidebarGroup] }],
    }),
  ],
});
```

The names are Griffe's own and they differ per parser; see
[Griffe's docstring parser options](https://mkdocstrings.github.io/griffe/reference/docstrings/).
Options are part of the extraction cache key, so changing one re-extracts the package.

## Sections that render

Whatever the style, Griffe produces the same structured sections, and each renders as its own
block in docstring order:

| Section                                       | Rendered as                                                                |
| --------------------------------------------- | -------------------------------------------------------------------------- |
| Prose                                         | Markdown, through the site's own processor                                 |
| Parameters, other parameters, type parameters | A table of name, type, default and description, with linked types          |
| Attributes                                    | The same table without the default column                                  |
| Returns, yields, receives                     | A list of typed values with their descriptions                             |
| Raises, warns                                 | A list of exception types, each linked where it resolves                   |
| Examples                                      | Prose and doctest blocks, in the order they were written                   |
| Admonitions (`Note:`, `Warning:`, `Tip:` …)   | An aside, in one of four flavours matching Starlight's own                 |
| Deprecations                                  | A badge on the heading and a caution aside carrying the explanation        |
| Functions, classes, modules, type aliases     | A list of cross-referenced names, as numpy-style `See Also` blocks produce |

Sections of a kind we do not model are ignored rather than guessed at, so a future Griffe
release can add one without breaking a page.

Parameter tables list the parameters the docstring documents; a parameter you leave out of the
docstring still appears in the signature above. Types come from the annotation when the
docstring gives none, and they are linked exactly as the types in the signature are; see
[Cross-references](/starlight-pydocs/guides/cross-references/).

## Admonition flavours

Griffe records an admonition's annotation (`note`, `warning`, `danger`, `seealso`, `hint`, …),
and each maps onto one of four asides styled to match Starlight's: note, tip, caution and
danger. An annotation we do not recognise renders as a note, keeping its own title.
`Deprecated:` blocks are the exception: the google parser routes them through the admonition
machinery, and they are turned into the deprecation notice instead of an aside, so the badge
and the explanation stay together.

## Doctests and examples

An `Examples:` section arrives as a sequence of prose and transcript pieces. Prose renders as
Markdown. A `>>>` transcript arrives unfenced, so it is fenced as `python` before rendering,
which means it is highlighted by whatever highlighter the site already uses: Expressive Code
under Starlight, plain Shiki in a bare Astro project.

`python` rather than mkdocstrings' `pycon`: no Python-console grammar ships in the Shiki
bundles these processors use, and `python` highlights a transcript correctly. A block that is
already fenced in the docstring is left exactly as written, so you can pick your own language:

````python "console"
def summarise(rows):
    """Summarise a table.

    Examples:
        The plain transcript form, fenced as `python` for you:

        >>> summarise([{"n": 1}])
        'n=1'

        Or fence it yourself, in any language:

        ```console
        $ python -m mypkg summarise rows.json
        n=1
        ```
    """
````

The `llms.txt` rendition of the same content fences transcripts as `pycon` instead, because
that output is read by machines rather than highlighted by Shiki.

## Prose rendering

Docstring Markdown goes through the markdown processor **your site has configured**, not one
this package brings along. Whatever your site does to its own Markdown (the theme, the plugins
Starlight registers, a mermaid plugin you added, GFM tables, smart quotes) happens to docstring
prose too, so an API page reads like the rest of the site.

Two consequences:

- Rendering happens once per build, at `astro:config:done`, after every integration has finished
  configuring the pipeline. The HTML lands in a sidecar file beside the cached dump, so no markdown
  engine runs while pages render.
- A docstring that cannot be rendered costs that one string. The build logs a warning, the object
  keeps its signature, parameters and links, and the page still exists.

Sätteri (the Astro 7 default) and the unified pipeline from `@astrojs/markdown-remark` are both
supported, because neither is a dependency here: the plugin calls whatever
`markdown.processor` resolves to. This documentation site runs the default; the
`examples/vanilla` site in the repository pins `unified()`, so both are exercised in CI.
